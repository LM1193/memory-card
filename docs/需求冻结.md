## 二、冻结的 MVP 需求（不可再缩小）

| # | 需求 | 验收方式 |
|---|---|---|
| 1 | 6 种牌面 × 各 2 张 = 12 张，3 行 4 列，位置由课件公式算出 | 对照公式手算 2 张位置一致 |
| 2 | 点 Start → 洗牌铺牌、开始计时 | 每次 Play 分布不同 |
| 3 | 单击背面牌翻正面，同屏最多 2 张正面 | 快速连点第 3 张无反应 |
| 4 | 配对成功：保持正面 + 锁定 + 得分 +1 | 已配对牌点击无反应 |
| 5 | 配对失败：1.5 s 后自动翻回 | 计时观察 |
| 6 | 6 对全配对 → 停表 → 胜利面板（victory 图 + 用时 + 得分） | 打完一局 |
| 7 | Restart 可重开（重新洗牌、清零计时与分数） | 连打两局 |
| 8 | WebGL 构建并部署 GitHub Pages，链接可玩 | 浏览器实测 |

## 三、本期砍掉（因两周工期，从初版"可选"升级为"必砍"）

| 砍掉项 | 原因 |
|---|---|

| 卡牌翻转动画 | +4~5 h，两周内不划算 |
| 4×4 难度 | 代码已预留 `rows/cols`，改配置即可，但本期不验证 |
| 最佳纪录 UI 展示 | `PlayerPrefs` 逻辑已写但不做界面展示 |

| 3D 化 / URP | 与 2D 目标无关 |
| 道具 / 成就 / 多语言 | 与完成度无关 |
| 重画美术 | 素材已足够（美术时间盒 ≤ 总时长 15%） |
| 复杂粒子 / 特效 | 时间黑洞 |
| 移动端原生打包 | WebGL 已满足交付需求 |

## 四、时间盒（每个里程碑的硬上限）

| 里程碑 | 上限 | 到点动作（降级为最小可交付） |
|---|---|---|
| M1 静态牌桌 | 4 h | 只要 12 张卡背摆对位置，背景与相机凑合即可 |
| M2 可翻牌 | 4 h | 只要点击能换图，不要求洗牌 |
| M3 完整一局可玩 | 5 h | 只要"能配对 + 1.5 s 翻回"，计分可先用 Debug 打印 |
| M4 闭环体验 | 4 h | 面板不做动画，纯数字 UI |
| M5 稳定性 | 4 h | 只跑"连点"与"点已配对"两条用例 |
| M6 在线可玩 | 5 h | 至少出 Windows 包 + 本地 WebGL 目录，链接顺延 |
| M7 实验报告 | 3 h | 先交设计思路 + 关键代码，截图与心得后补 |

**总预算约 29 h**，两周内平均每天约 2 h。

## 五、进度吃紧时的让位顺序（已确认）

```
先保 M1 → M2 → M3（可玩是底线）
  → 再保 M4（闭环体验）
    → M5 可压缩为两条用例
      → M6 可降级为本地构建，链接顺延
        → M7 可先交报告框架
```

> 两周内的成功口径：**能玩完整一局 → 有计时与结算 → 能构建**。链接与报告尽力准时，冲突时按上述顺序让位。

## 六、需求变更流程

1. 新想法记入下方待办池，写清价值与预估工时；

3. 仅"阻断性 bug 修复"与"数值调整"允许立即动手；
4. 其余全部顺延到下一个项目。
